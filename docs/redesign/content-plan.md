# 内容策划：烁烁（SSS）

站点定位：一个前端开发者的个人技术博客。站名「烁烁」，副标题「记录自己的一切」，作者「烁」。

语气基线：第一人称，具体，允许自嘲，不端着。写数字不写形容词。不写"首先/其次/最后"，不做鸡汤结尾。全站简中。

### 写作分工的意图

- 第 1、3 篇负责"可信度"：给出代码、版本号、构建耗时、报错原文。访客判断一个技术博客值不值得订阅，看的是这类细节里有没有"只有真做过才知道"的东西。
- 第 4 篇负责"观点"：有明确立场（大多数赛博朋克网页是廉价而不是风格），会被讨论，也最容易被引用。给站点定调——这个博主是会骂人的，不是通稿机器。
- 第 2 篇负责"入口流量"：工具清单是长尾搜索最集中的体裁，也是同类站点互相链接最多的内容类型。
- 第 5 篇负责"人味"：不追关键词，让前四篇的硬内容里有一个出口。

刻意不做的事：

- **不抢「Astro 教程」这种大词。** 单篇博客抢不过官方文档和专栏，写「Astro 5 内容集合怎么用」这种具体到报错信息的词，反而能进前五。

色值使用边界（与 `docs/redesign/design-spec.md` §6.23-B 对齐）：

- 五个文章主色**只存在于封面图内部**，不进 UI 文字层。全站 UI 强调色只有青 / 紫两档，遵守「每屏一处冷光源」。
- 深蓝 `#3b5bdb` 对页面底色仅 3.41:1，**不可作文字色**；若 UI 层需要蓝，用 `#8b9dff`（6.9:1）。所以深夜篇的封面可以偏蓝，但 UI 侧不会有蓝色文字。
- 每篇文章另有一条极窄 `--article-accent` 通道，仅允许出现在三处：卡片 hover 的 2px 左缘条、详情页标题下 48×2px 短横线、封面图本身。

封面相邻配色（与 `design-spec.md` §6.23-C 对齐）：

当前时间倒序排下来是「冷灰 → 洋红 → 黄 → 冷紫蓝」，相邻组合里没有「洋红 × 青」这种互斥对，**现状不需要任何调整**。规则留给以后：新加文章时如果正好撞上「洋红 × 青」相邻，把其中一张的底色压成中性深灰、只保留一处小面积 accent，不要为了配色去动文章顺序（顺序是内容约定，不是视觉变量）。

出图时的一条硬信息：**所有封面在页面上都会被统一压暗**（`brightness(0.92) saturate(0.88)`，置顶卡 `0.94 / 0.90`，另叠一层 6% 页面底色）。所以做图时按规范色值出满饱和即可，**不要提前降饱和、也不要自带暗角**——提前压暗的图进页面会被压第二次，出来是脏的；反过来把色做足不会被压坏，`#38f5d0` 压到 0.88 后约等于 `#34e0bf`，仍在霓虹色的可用范围里。封面上的大字也别贴在极暗角落，压 8% 之后容易糊成背景。

封面已落地：5 张 webp 在 `src/assets/covers/<slug>.webp`，frontmatter 的 `cover` 写相对路径 `../../assets/covers/<slug>.webp`（走 `image()` 正规通路）。**不要写成 `/img/...`**——那会让 `content.config.ts` 里的 `image()` 试图把 public 路径当资源导入，构建直接报 `[ImageNotFound]`，这是踩过一次的坑。`public/img/cover/cyber/{life,note,tools}.webp` 是分类封面，走 public 字符串路径，与文章 cover 是两条独立通路，不要混。

## 五、文案关键取舍

1. **不写"欢迎来到我的博客"。** 首页首屏只有站名和副标题，关于页第一句直接是"我是烁，白天写业务前端"。访客不需要被欢迎，他需要知道这是谁的地盘。
2. **技术文章全部给数字，不给形容。** 写成"构建 4 分 12 秒降到 38 秒""配置文件 412 行剩 60 行""8 小时迁完"，而不是"大幅提升""显著优化"。数字是可以被验证的，也是这类读者唯一相信的东西。
3. **赛博朋克那篇故意不给完整方案。** 它是随笔不是教程，给的是三个判断标准和一个自检清单。如果写成 step-by-step，会变成一篇平庸的 CSS 教程，也抢不到那个词。
4. **工具清单不排榜单。** 没有"第一名""强烈推荐"，只有"我拿它干什么"。这样即使读者不同意，也不会觉得被推销。
5. **关于页不写"热爱技术、拥抱开源"。** 换成"日活三十人，二十个是我在不同设备上的自己"这种自嘲，可信度比形容词高。
6. **深夜那篇不升华。** 结尾停在"我又该关电脑了"，不给人生道理。前面说了"它不健康、也不高效"，就不该再收一个正能量的尾。

## 必须由用户提供的真实信息清单

以下是我按行业惯例先写了、但**必须替换成你本人真实情况**的：

1. **页脚的社交链接（最高优先级，且已构成事实错误）** —— 关于页现在**不写死任何邮箱和 GitHub 地址**，只说"页脚的图标能找到我"。但 `config/site.yaml` 的 `social` 仍是模板值：`mailto:your-email@example.com`、`https://github.com/your-username`、`https://t.me/your-handle`、`https://x.com/your-handle`。构建产物里每个页面都带这两次 `mailto:your-email@example.com`，也就是说**这句话目前在每个页面上都是假的**，点页脚邮箱会打开一个不存在的地址。只有 `rss: /rss.xml` 是真的。
2. **GitHub 真实主页** —— 同上，关于页故意不写 URL，就是为了避免上线一个 404 或假账号。
3. **关于页的三段个人经历** —— 「2020 年开始写代码」「做过三年后台管理系统」「把一个跑了五年的前端仓库从 jQuery 里捞出来」。这三条是示例性履历，必须换成你的真实经历，否则被熟人看到会很尴尬。
4. **工具箱的真实状态** —— 「日活三十人，二十个是我在不同设备上的自己」「纯本地记账工具还没写完」。如果这些项目不存在，这两段要删掉或改写。
5. **工具清单里的使用细节** —— 八个工具的选择是真实的软件，但"用 Ditto 固定六条片段""Obsidian 300 篇笔记""Zed 冷启动 0.4 秒"这类细节是我的设定值，请按你的实际用法调整，或直接保留（不影响可用性，但会变成"别人的博客"）。
6. **头像** —— `/img/avatar.svg` 若仍是模板图，需要换成真实头像或原创图形。
7. **建站年份与地址** —— `startYear: 2026`、`url: https://qiyuan.icu`，与页脚版权、canonical 相关，确认无误。

## 需要你拍板的两个决策
